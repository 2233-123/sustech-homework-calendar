# 作业日程 — 缩放体验增强设计（rev5）

> 本文档针对「窗口缩放」的交互体验四项诉求给出方案设计，随后按既定流程实施（实现 → 规格审查 → 质量审查 → 视觉走查与调整 → 全量终审 → 合并推送）。

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-13 |
| 分支 | `feature/win-rev5`（基于 master @ `fd929c0`） |
| 基线 | rev4 已完成并推送（backend 120 / frontend 21 全绿；缩放已实时数值、但**松手才生效**、无最小字号约束） |
| 需求 | ① 缩放拖动**即刻生效**（不必等松手）+ 流畅动画；② 缩放后**光标仍停在缩放条上**便于继续调整；③ 设定**最小字号**——继续缩小时字号不再下降、横向继续收窄、纵向用**滚动条**（滚轮浏览）；④ 用**视觉模型模仿用户习惯**走查并调整表现形式 |

---

## 1. 需求拆解

| # | 用户原文要点 | 目标定义 |
|---|---|---|
| R1 | 「窗口缩放可不可以像窗口透明度一样即刻显示效果，辅以流畅的动画效果，而不用等到松手」 | `input`（拖动中）节流下发缩放；主进程对尺寸/zoom 做平滑逼近（非跳变） |
| R2 | 「缩放后应该保证鼠标光标依然在窗口缩放的那个条上，方便继续调整」 | 拖动期间锚定「滑条行」的屏幕坐标：每次缩放后自动微调窗口位置，使滑条行不动 |
| R3 | 「设定一个最小字号…若继续缩放则不再降低字号，横向继续缩小，纵向则用滑动条让用户能够通过鼠标滚轮浏览所有信息」 | zoom 设下限 `MIN_ZOOM`；低于阈值后视口宽度继续收窄（内容重排）、高度变矮 → 页面纵向可滚动（细滚动条 + 滚轮） |
| R4 | 「调用视觉模型模仿用户习惯，调整表现形式」 | 实现后截取各档位/拖动中画面，用 `vision.js` 以普通用户视角评审可读性/可操作性/布局，按结论调整表现 |

## 2. 现状与约束

- rev4 起：`window_scale` 决定内容尺寸，`webContents.setZoomFactor(内容宽/408)` 同步内容缩放（任意档位布局视口恒 ~408 宽）；缩放**在 `change`（松手）后才应用**。
- 无边框窗口（`resizable:false`），位置经 `window_pos` 持久化（`moved` 防抖 500ms），启动与缩放钳制到工作区。
- rev2 R1 约定：正常态**无滚动条**（`html,body{overflow:hidden}`、`*::-webkit-scrollbar{display:none}`）——紧凑态属新增状态，需单独放开。
- `system`：Windows 11 + 150% DPI；Electron 44；既有验证工具：WMI 启动 + CDP + 截图 + 像素扫描 + `vision.js`。

## 3. 方案设计

### 3.1 实时缩放 + 平滑动画（R1）

- 渲染层：`#s-scale` 的 `input` 事件 → 更新读数 + **节流 ~60ms** 调用 `hwShell.setWindowScale(p)`（复用透明度滑条的节流+尾沿模式）；`change`（松手）→ 立即下发终值 + `PUT {window_scale}` 写穿（持久化仍只在松手时发生）。
- 主进程：`shell:set-window-scale` 改为「设定目标」而非直接落地——维护 `currentScale → targetScale` 的平滑循环（~16ms/帧，步长 0.35，收敛 |Δ|<0.5% 后停止）：
  - 每帧由 `s` 计算：`zoom = max(s/100, MIN_ZOOM)`；`W = round(408×s/100)`、`H = round(760×s/100)`，再按工作区比例钳制；
  - 每帧应用 `setContentSize(W,H)` + `setZoomFactor(zoom)`（同一 `s` 派生，保证视口 = `W/zoom × H/zoom` 自洽）。
- 取舍：zoom 每帧变化会触发重排（本应用 DOM 极小，成本可接受）；若实测存在抖动，退化为「尺寸平滑、zoom 按目标值」——由 §3.5 视觉走查判定。

### 3.2 光标锚定（R2）

目标：拖动期间「滑条行」在屏幕上的位置保持不动（光标一直压在滑条上）。

- 新增 IPC：`shell:get-window-info` → `{x,y,width,height}`（DIP，`getBounds()`）；`shell:nudge-window` → 按增量移动窗口（工作区钳制）。
- 渲染层锚定流程：
  1. `pointerdown`（拖拽开始）时记录锚点：`zoom = width / window.innerWidth`；`anchor = { x: info.x + rectCx×zoom, y: info.y + rectCy×zoom }`（`rect` = `#s-scale` 的 `getBoundingClientRect()` 中心）；
  2. 每次 `setWindowScale` 返回/查询到新 bounds 后，`requestAnimationFrame` 再测滑条新位置：`dx = anchor.x − (newX + newRectCx×newZoom)`，`dy` 同理；`|d|>0.5` 时调 `shell:nudge-window`；
  3. `pointerup/change` 结束锚定。
- 已知边界：窗口贴屏幕边缘时钳制会破坏完美锚定（记录为已知限制）；`moved` 防抖会把最终位置写回 `window_pos`（无需额外处理）。

### 3.3 最小字号与紧凑模式（R3）

- **阈值**：`MIN_ZOOM = 0.7`（初值）：基准最小正文 12px × 0.7 = 8.4 CSS px（@150% DPI ≈ 12.6 物理 px），先按此落地，**以 §3.5 视觉走查结论定档**。
- `s ≥ 70%`：行为同 rev4（zoom = s/100，视口恒 408 宽，整体等比缩放）。
- `s < 70%`：**zoom 固定 0.7**；窗口继续按 `s` 收窄 → 视口宽 = `408×s/70`（40% 时 ≈233px）、视口高 = `760×s/70`（40% 时 ≈434px）：
  - **横向继续缩小**：内容在更窄视口里重排（日历格、日列表标题换行、弹层自适应）；
  - **纵向溢出可滚动**：`body.compact` 下放开滚动——`overflow-y:auto` + 6px 细滚动条（`::-webkit-scrollbar` 在 compact 下恢复显示）+ 滚轮可滚动；`.widget` 高度改自然高度、日历行高固定、`.day-list` 取消内部滚动（由页面统一滚动）。
  - 切换由渲染层在每次缩放时 `document.body.classList.toggle('compact', p < 70)`（确定性，不依赖测量）。
- 预期需适配点（由走查确认）：`.remind-row`/`.slider-row` 在 ~200px 视口下的换行、`.modal-card` 宽度、标题栏元素拥挤。

### 3.4 与既有机制的关系

- 持久化、工作区钳制、`window_pos` 记忆、贴边收起/唤出、透明度滑条均不变；平滑循环在收起/恢复时停止（`hideToEdge` 前收敛或直接落定）。
- 读数为「标称档位」；尺寸仍以 IPC 实测值回填（rev4 行为保持）。

### 3.5 视觉模型走查与调整（R4，T2 任务）

- 素材：40% / 50% / 70% / 100% / 150% 五档 × {主界面、设置面板、拖动中} ≈ 15 张截图（真实 Electron + CDP + 截屏）。
- 方法：`vision.js` 以「普通用户习惯」提问：字号是否看得清、元素是否挤/溢出、滚动是否可发现、拖动体验是否自然；逐档产出评审结论。
- 调整：据结论修正 `MIN_ZOOM`、紧凑阈值、间距/换行样式、滚动条可见性等（小步提交），直至通过。

## 5. 验收标准

1. 回归：backend 120 / frontend 21 全绿；`node --check` 通过。
2. **R1**：拖动缩放条过程中窗口**持续变化**（非松手才变）；主进程平滑（无肉眼跳变）；松手后写穿持久化、重启生效。
3. **R2**：拖动全程滑条行屏幕位置漂移 ≤ 2px（**稳态**）；快速拖动允许瞬态 ≤ ~14px 且自愈（工作区边缘钳制场景除外，需注明）。
4. **R3**：`≥70%` 等比缩放；`<70%` 时字号不再变小、视口横向继续收窄、出现细滚动条且**滚轮可浏览全部内容**（含日列表底部）；40% 时主要文字可读（走查判定）。
5. **R4**：五档 × 三态走查完成，调整项落地并复评通过。
6. 测试隔离 + 进程/端口零残留 + 无凭据落盘。

## 6. 风险与边界

- 每帧 `setZoomFactor` 的重排成本：DOM 小，预期可接受；实测抖动则降级（§3.1）。
- 锚定与工作区钳制冲突时允许 ≤ 钳制量 的漂移（记录）。
- 紧凑模式与 rev2「无滚动条」的外观约定并存：滚动条仅在 compact 态出现。
- 低档位（<50%）下即使字号保底，物理尺寸仍小（屏幕像素限制），属固有限制。

## 7. 实测记录（T1/T2 真机与视觉走查）

### 7.1 T1 交互与机制（隔离真机，12 条日程）

- **实时性/平滑**：按住 100%→40% 期间实测 33–44 种窗口尺寸持续变化；相邻跳变最大 8.4%（≤45% 阈值）。
- **命中与可见性**：拖动全程 `elementFromPoint(滑条中心)` 命中且滑条在视口内（弹层钉视口修复后，含低档位；卡片不再落出窗口）。
- **锚定**：稳态漂移 0.58px（86% 采样 ≤2px）；快速拖动瞬态峰值 ≤13.3px、自愈（见 7.3）。
- **compact/最小字号**：40% 时 `zoom≈0.700`、视口 ≈234×434、**6px 细滚动条经像素级验证**、滚轮可浏览全部 12 条内容、日历格高 26px。
- **持久化**：写入 40 重启 → compact+zoom 生效；`window_scale/window_pos/opacity` 键完整。

### 7.2 T2 视觉模型用户视角走查（40/50/70/100/150% × 主界面/设置/拖动中，15 张）

- 视觉模型在 **40%/50% 主界面**判定「日历日期严重裁切/重叠……根本无法看清」「不像正常可用的桌面小工具」——定位到真实缺陷：compact 下 `.calendar` 被 flex 压缩（等价态实测 23px 行高；修复规则后 26px 且无裁切）。
- 修复 `body.compact .calendar { flex:none; grid-auto-rows: minmax(26px, auto); }` 后复评：「日期数字清晰可见、无遮挡裁切」「非常像正常可用的桌面小工具」。
- 同步调整：滚动条对比度 .5→.62；键盘/程序化改档路径可见性改为 80ms 轮询至收敛。
- `MIN_ZOOM` 维持 0.7（40% 文字判定「可辨、偏小」；该档为极端档位，日常建议 ≥60%）。

### 7.3 遗留（非阻塞）

- 快速拖动瞬态锚定漂移峰值 ≤13.3px（稳态 0.58px，自愈）；
- 拖动中读数偶有 ±5 档回跳（窗口重排期间刻度重映射，终值正确）；
- T2 提交说明中「日历被压成 ~10px」的表述与复核实测（23px 等价态）不符；代码修复本身成立。
